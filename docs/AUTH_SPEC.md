# Phase 3 Specification: Authentication, Per-User Data and Rate Limiting

> Written before the code. Section 11 links each requirement to its implementation and tests.

## 1. Problem and goal
Until now anyone who could reach the API could read every conversation and document and spend the operator's model credits. Goal: accounts, strict per-user data separation, and request limits, so the service can be exposed beyond a laptop. Out of scope: email verification, password reset, multi-factor authentication, social login, roles/admin, organisations.

## 2. Requirements
| ID | Requirement | Acceptance criteria |
| --- | --- | --- |
| A-1 | Register | `POST /api/auth/register {username, password}` creates a user and returns a session token; duplicate username is 409; username 3 to 32 chars of letters, digits, `_ . -`; password 8 to 128 chars |
| A-2 | Log in | Correct credentials return a token; wrong username or password return the same 401 message |
| A-3 | Protected API | Every `/api/*` data endpoint returns 401 without a valid token |
| A-4 | Log out | `POST /api/auth/logout` makes the token unusable immediately |
| A-5 | Data isolation | A user can list, read, delete and continue only their own conversations and documents; other users' ids return 404 |
| A-6 | Scoped retrieval | RAG searches only the caller's documents |
| A-7 | Chat rate limit | At most `RATE_LIMIT_CHAT_PER_MIN` chat requests per user per minute; excess returns 429 with `Retry-After` |
| A-8 | Login rate limit | At most `RATE_LIMIT_AUTH_PER_MIN` register/login attempts per client IP per minute |
| A-9 | Password storage | Only salted, slow hashes are stored; no plain text anywhere |
| A-10 | Local mode | `AUTH_REQUIRED=false` runs as one built-in user for personal use and demos |
| A-11 | Safe default | Authentication is required unless explicitly turned off |

## 3. Design decisions
### 3.1 Password hashing
`scrypt` from the Python standard library (memory-hard, so GPUs and ASICs gain little), cost N=2^15, r=8, p=3 (an OWASP-listed combination), 16-byte random salt per user, stored as `scrypt$N$r$p$salt$hash` so parameters can be raised later and old hashes still verify. Comparison uses `hmac.compare_digest` (constant time). **Alternatives:** **Argon2id** (the current first choice in OWASP guidance; needs a third-party package, so I chose the stdlib option and would switch for production), **bcrypt** (older, 72-byte input limit), **PBKDF2** (acceptable, not memory-hard), and **plain or fast hashes like SHA-256 (never, they are cheap to brute force)**.

### 3.2 Sessions: opaque server-side tokens, not JWTs
Login creates a random 256-bit token (`secrets.token_urlsafe(32)`). Only its SHA-256 hash is stored, with the user and an expiry (default 7 days), so a database leak does not leak usable tokens (the token is high-entropy, so a fast hash is appropriate here, unlike passwords). Each request looks the token up. **Why not JWT:** a JWT cannot be revoked before expiry without a server-side list, which removes its main advantage; logout and "kill this session" matter more here than avoiding one indexed lookup. **JWT fits** when many independent services must verify identity without calling a central store. **Alternatives:** OpenID Connect with an identity provider (Auth0, Keycloak, Google, Entra ID: best for real products, no password handling at all), API keys for machine clients, passkeys/WebAuthn, magic-link email login.

### 3.3 Token transport
`Authorization: Bearer <token>`, kept in `sessionStorage` by the UI. **Trade-off:** script-readable storage is exposed to cross-site scripting; mitigated by never inserting model or user text as HTML (`textContent`). **Alternative:** an `HttpOnly; Secure; SameSite` cookie (not readable by scripts) which then needs CSRF protection; preferable once the UI grows.

### 3.4 Authorization (preventing insecure direct object references)
Every query that touches user data includes `user_id` in its `WHERE` clause, so ownership is enforced where the data is read, not only in the route. Another user's id returns **404, not 403**, so the API does not reveal that the id exists. New conversation and document ids are generated by the server. `save_exchange` re-checks ownership before writing.

### 3.5 Data model changes
`users(id, username UNIQUE NOCASE, password_hash, created_at)`, `sessions(token_hash PK, user_id → users, created_at, expires_at)`; `conversations.user_id` and `documents.user_id` reference `users` with cascade delete. All DDL now lives in one `init_db`. There are **no migrations yet**: a database created by an earlier version is detected and rejected with a clear message (delete it or migrate); Alembic is the proper tool.

### 3.6 Rate limiting: token bucket
Each key (user id for chat, client IP for login/register) owns a bucket of capacity `limit` tokens that refills at `limit/60` tokens per second; a request spends one token, and is rejected with `Retry-After = ceil((1 - tokens) / rate)` seconds when empty. This allows short bursts yet enforces the average rate, unlike a fixed window (which permits double bursts at window edges). Implementation: in-process dictionary guarded by a lock, injectable clock for tests, idle keys pruned. **Limits:** in-process state is per worker and lost on restart, so with several workers the effective limit multiplies; the production answer is a shared store (Redis with an atomic script, or an API gateway). The client IP comes from the socket; `X-Forwarded-For` is **not** trusted, because clients can forge it. Behind a reverse proxy, configure the server's trusted-proxy setting instead. Spend caps (tokens per day) are a separate, later feature.

### 3.7 Timing and enumeration
Login for an unknown username still runs a password hash against a dummy value, so response time does not reveal which usernames exist. Registration does reveal taken names (409); accepted for usability, and rate limited.

## 4. Threat model
| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| Password guessing / credential stuffing | Per-IP limit, slow hash, no composition rules but 8+ length | Distributed attacks; add per-username lockout/backoff, breached-password check, MFA |
| Stolen database | Salted scrypt hashes; only token hashes stored | Weak passwords still crackable offline |
| Stolen token | Expiry, logout revocation, HTTPS required in deployment | No device list or "log out everywhere" yet |
| Reading others' data | `user_id` in every query, 404 for foreign ids, tests for each endpoint | Any new endpoint must follow the rule |
| CSRF | Not applicable to bearer headers (browsers do not attach them automatically) | Applies if cookies are adopted |
| Cross-site scripting | `textContent` rendering | Markdown rendering would need sanitising |
| Cost abuse by a valid user | Chat rate limit | No daily token budget yet |
| Traffic over plain HTTP | Out of the app's control: terminate TLS at the proxy | Documented as a deployment requirement |

## 5. Alternatives summary
Build vs buy: writing auth by hand is educational but a managed identity provider is usually the better engineering decision for a product. This phase exists to show understanding of the mechanisms (hashing, sessions, authorisation, throttling).

## 6. Configuration
`AUTH_REQUIRED` (true), `ALLOW_REGISTRATION` (true), `SESSION_DAYS` (7), `RATE_LIMIT_CHAT_PER_MIN` (20; 0 disables), `RATE_LIMIT_AUTH_PER_MIN` (10; 0 disables).

## 7. API additions
`POST /api/auth/register`, `POST /api/auth/login` → `201/200 {token, user:{id, username}}`; `POST /api/auth/logout`; `GET /api/auth/me`. New statuses: 401 (missing or invalid token), 409 (username taken), 429 (rate limited, with `Retry-After`).

## 8. UI
Sign-in panel (login or register), token kept in `sessionStorage`, logout button, automatic return to sign-in on 401.

## 9. Limitations
No email verification, password reset, MFA, account deletion or roles; sessions table is not purged of expired rows; rate limiter is single-process; scrypt instead of Argon2id; SQLite remains single-node.

## 10. Failure behaviour
Bad token → 401 (UI shows sign-in); limiter exceeded → 429 and nothing is processed; database error on login → 500 with no detail leaked.
